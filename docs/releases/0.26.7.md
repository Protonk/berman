# 0.26.7

Berman is described as a tool for intermittent management of work in a
software project. Someone responsible for a project commissions a bounded
engagement in its Git checkout, a worker does the assigned work through Codex
or Claude and keeps the account the assignment asks for, and Berman preserves
the commission and the evidence it can collect. Releases through 0.26.6
described Berman as support for participant observation of software
development. Research remains a use of Berman, set up in a study's own
instructions, and is no longer presented as what every installation does.

This release changes that description and the wording Berman prints. It
changes no command, option, setting, schema, record format or step of the
lifecycle.

## For operators

- The guides name two roles where they said researcher. The commissioner
  decides an engagement: what is assigned, when a sitting starts and when the
  engagement ends. The operator runs the commands and is often the same
  person. An installation whose own guidance says researcher for the person
  who decides can keep that word: it names the commissioner.
- Printed text changed, and a script that matches these sentences needs the
  new wording. The cheatsheet's steps for a prepared run, for ending an
  engagement and for commissioning say commissioner or engagement where they
  said researcher or fieldwork, and so does the note `prepare` prints. The
  first line of `berman --help` says what Berman is, and the help for
  `commission --request`, `end`, `exposure` and `closeout --reason` is
  reworded. Seven messages are reworded: closeout or collection without a
  recorded ending (two), the `--missing-reason` hint, an ending without a
  reason, a commission with neither recipe nor plan, a plan outside the study
  and a plan with an invalid identity. What each command accepts and refuses,
  JSON keys, cheatsheet states such as `in fieldwork`, and exit codes are
  unchanged.
- These names keep their earlier form because commands, paths, schemas and
  published records carry them: `berman-research`, the guest directory
  `~/research/`, `scripts/install-research-wheel`, `berman.research-plan/1`,
  the recipe label `participant-inquiry/1`, the `exposure` command, the
  `berman-analysis/` folder, the FIELDWORK headings and "participant notes"
  inside reading editions, and the words study and fieldwork.
- A recipe must still declare `recording_protocol` as `work-accounts/1` or
  `participant-inquiry/1`. Berman treats both alike, and the limits now say
  so.
- The example study's baseline instructions address the account to the person
  who commissioned the work, where they said it was for research. A second
  recipe, `project-review`, shows an assignment that sets the work. A study
  that copied the earlier baseline keeps its own copy.
- The operating guide gains the words Berman uses and a section on using it
  for research. The custody guide lists what is recorded and says that a
  verified recording establishes nothing about the quality of the work or the
  accuracy of a worker's account. Keeping recordings and what is written from
  them away from the project is described as a study's choice, where it read
  as a rule for every installation.
- The limits now state that a plan commission that is never launched holds
  its plan. The behavior is that of 0.26.6.

## Adopting it

Install the same wheel in the guest and in a host environment. The
controller's ledger, the connector settings and the `recording/3` and
`reading-edition/3` formats are unchanged from 0.26.6, so an existing study is
read as it is, and a study's own recipes, plans and connections need no change.

`cheatsheet.py`, `cli.py`, `connector.py`, `controller.py`, `study.py` and the
description in `schemas/research-plan-1.json` changed. No file under
`executor/` or `archive/` changed, nor `custody.py`, `evidence.py`,
`protocol.py` or `files.py`, so the hook, the collection and the edition
builder have the bytes of 0.26.6 and new editions record the same builder
digests. The installation's source digest is new, and so is the set of module
digests in each preparation and launch receipt. A native qualification applies
only to the bytes it observed: take native evidence from the adopting
installation. The form of the hook command is unchanged. A host environment at
a new path has a new interpreter path in its hook commands, which then need
installing and a review in the actual Codex CLI.
[Executor qualification](https://github.com/Protonk/berman/blob/v0.26.7/docs/executor.md#qualification-evidence)

## For developers

- AGENTS.md states what Berman is described as and lists the interface names
  that keep research wording. Renaming one is an interface change.
- The package description reads "Intermittent management of work in a
  software project: commission bounded engagements and preserve a verifiable
  record of each."

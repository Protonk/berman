# 0.26.6

`berman cheatsheet` is the operator's starting point. It reads a study's
recorded situation from the guest and prints the commands that apply now,
written out for the installation that ran it. The package and its documentation
are arranged around the executor, the connector and the research side.

## For operators

- `berman cheatsheet`, also `berman-research cheatsheet`, sends one `status`
  to the guest and writes nothing. It names the packet a prepared run is
  waiting on, a sitting with no recorded exit, an open supplement and an
  unreachable guest. With no study connected it says how to check the
  installation and connect one. It prints a full path instead of a bare
  `berman` whenever `PATH` would lead to another installation.
- `prepare` prints the packet path and the launch command on stderr, beside the
  guest's receipt on stdout.
- `status` without a run adds `harness`, `sittings` and `supplements` to each
  row.
- `berman verify` reports `passed` and `checks` in its JSON. The `--software`
  flag and the terminal formatting settings of 0.26.5 are gone.
- New recordings are `berman.recording/3` and new editions
  `berman.reading-edition/3`. 0.26.5 and earlier cannot read them. This release
  still verifies guest `recording/2` and single-recording `reading-edition/2`,
  so a study's earlier guest runs keep verifying in place.
- A recording's coverage names the callbacks that had no transcript and the
  ones that obtained a verified snapshot. A failed sitting is preserved when
  associated-session discovery was unavailable. An interrupted sitting stays
  open while its process identity is uncertain.
- Project checks take string arguments and the placeholders listed in the
  executor guide. Each plan step needs a string identity and a recipe.

## Adopting it

Install the same wheel in the guest and in a host environment of its own. The
controller's ledger and the connector settings are unchanged from 0.26.4 and
0.26.5, so an existing study is read as it is. The cheatsheet also reads a
controller of either release, whose overview lacks the new `status` fields.

Executor module paths and bytes changed, so the module digests in its
preparation and launch receipts differ. A new host environment also has a new
interpreter path in its hook commands, and the SessionEnd and Interrupt hooks
now ask for three seconds, the most Codex grants them, in place of thirty.
`codex-hooks --home HOME --merge` prints the whole `hooks.json` to install,
keeping unrelated hooks. Install it, review the hooks in the actual Codex CLI,
and take native evidence from the adopting installation. The form of the hook
command is unchanged:
`python -I -B -m berman.executor --spool SPOOL hook --home HOME`. The guest
entry points are unchanged: `python -I -m berman.controller` and
`python -I -m berman.custody`.

Like 0.26.5, this release does not open co-located workspaces or the records
of the releases that wrote them. Keep the runtime that wrote those for reading
them. [Executor qualification](https://github.com/Protonk/berman/blob/v0.26.6/docs/executor.md#qualification-evidence)

## For developers

- `berman.capture`, `berman.sources`, `berman.snapshots`, `berman.checks`,
  `berman.recipes` and `berman.config` are gone. Executor-only code is under
  `berman.executor` (`sources`, `snapshots`, `checkout`, `claude`, `codex`);
  recipes and plans are in `berman.study`.
- The layers contract refuses imports between the controller and the executor,
  and the whole executor is held to the standard library.
- `berman ci` qualifies one candidate wheel through the native executor and the
  SSH controller, with an optional live harness. It builds the candidate
  through a source distribution, so a stale `build/` directory cannot put
  removed modules into it, and it keeps the hook registration in its own Codex
  home on the candidate.
- `docs/usage.md` and the operator half of `docs/connector.md` are now
  `docs/operating.md`; the wire contract is `docs/protocol.md`.
